# 售后-订单状态联动规则 V1.0

> 本文档为**跨端统一规则**，定义「订单状态」与「售后申请」之间的联动关系，是各端售后管理、订单管理模块实现订单状态同步的**权威依据**。
>
> 适用端：商城运营后台、品牌商城、供应链管理后台、供应商管理后台。
>
> 相关文档：`doc/PRD-*-售后管理-V1.0.md`、`doc/业务逻辑清单-*-售后管理-V1.0.md`、`售后流程状态对照/`。

---

## 一、背景与案例 `V1.0`

### 1.1 问题案例

订单 `260724111900001`：处于"待发货"状态时用户申请退款（仅退款），售后审核通过后，**供应商端订单仍为"待发货"**，未被取消，导致供应商可能继续发货、与退款结果冲突。

### 1.2 根因

经核查 `doc/` 下全部 PRD 与业务逻辑清单，现有文档**只定义了"售后单 / 退货单"的状态流转，从未定义"订单（主/子订单）状态"如何随售后联动**（关键词「待发货 / 已取消 / 订单状态 / 撤销」在 `doc/` 下零命中）。系统缺乏"售后申请 → 订单状态联动"规则，导致上述 bug 必然发生。

### 1.3 修订目标

补齐联动规则：**订单处于"待发货"状态时用户发起仅退款，供应链 / 供应商端对应订单及时变为"已取消"**；售后被驳回或撤销后恢复"待发货"；退款成功后供应链/供应商保持"已取消"，运营端、品牌商城端订单同步进入"已关闭"终态。

---

## 二、关键前提：售后类型与订单状态的可发起关系 `V1.0`

> 这是理解本规则的前提。不同售后类型能在不同的订单状态下发起，**"待发货"状态下唯一能发起的售后类型是「仅退款」**。

| 售后类型 | 待发货 | 已发货（在途） | 已签收 |
|----------|:------:|:--------------:|:------:|
| **仅退款** | ✅ | ✅ | ✅ |
| **退货退款** | ❌ 无货可退 | ❌ 未签收无货可退 | ✅ |
| **换货** | ❌ 无货可换 | ❌ 未签收无货可换 | ✅ |

**结论**：

- "待发货"状态下，货尚未发出，**不可能发生退货退款、换货**（无货可退 / 可换）。
- 因此"待发货状态下发起的售后"**只能是「仅退款」**——案例 `260724111900001` 正是此场景。
- 退货退款、换货只能在用户已签收后发起，彼时订单早已离开"待发货"状态，**不属于本规则的"待发货 → 已取消"范畴**（详见第六章）。

## 三、适用范围 `V1.0`

| 维度 | 说明 |
|------|------|
| 适用场景 | **订单处于"待发货"状态时，用户发起「仅退款」** |
| 全流程联动端 | 供应链管理后台、供应商管理后台（发起即取消、驳回/撤销恢复、退款成功保持已取消） |
| 终态联动端 | 商城运营后台、品牌商城（**审核阶段不变；退款成功时订单变为「已关闭」**） |
| 联动粒度 | **子订单 / SKU 维度**：仅作用于被申请售后的那个子订单（SKU 行），同一主订单下其他商品行订单不受影响 |
| 联动对象 | 售后单所关联的子订单 / SKU 行的「订单状态」字段 |

## 四、联动规则总表 `V1.0`

> 仅适用"待发货 + 仅退款"场景。表中"供应链/供应商子订单状态"指售后单关联的子订单状态。

| 规则 | 触发事件 | 供应链 / 供应商 子订单状态 | 运营端订单 | 品牌商城端订单 |
|------|----------|---------------------------|------------|----------------|
| **R1** | 用户在订单"待发货"时发起仅退款（售后单 → 待商家审核） | 待发货 → **已取消** | 不变 | 不变 |
| **R2** | 该仅退款被驳回（售后单 → 已驳回） | 已取消 → **恢复待发货** | 不变 | 不变 |
| **R3** | 该仅退款被客户撤销（售后单 → 已撤销） | 已取消 → **恢复待发货** | 不变 | 不变 |
| **R4** | 该仅退款审核通过 → 退款成功（终态） | **保持已取消** | → **已关闭** | → **已关闭** |

### 4.1 规则要点

- **R1 是修复 `260724111900001` 类 bug 的核心**：仅退款申请一经提交（售后单进入"待商家审核"），供应链 / 供应商子订单**立即取消**，无需等待审核通过，从而拦截发货。
- **R2 / R3 恢复**：驳回（商家侧）或撤销（客户侧）意味着这笔订单仍需正常发货，故将被取消的子订单恢复为"待发货"，可继续履约。此时运营/品牌商城订单自始至终未变。
- **R4 终态关闭**：退款成功（不可逆）后，供应链/供应商子订单维持"已取消"；运营端、品牌商城端订单同步进入终态，展示为**「已关闭」**。

> **状态文案映射**：退款成功这一终态，在不同端的展示文案不同——供应链 / 供应商端为「已取消」，运营后台与品牌商城端为「已关闭」。两者**语义一致**（订单因退款成功而终止，不再履约 / 交易），仅各端命名差异。

### 4.2 为什么运营 / 品牌商城"审核阶段不变、退款成功才关"

- 供应链/供应商的"取消"是为了**拦发货**（动作指令），必须发起时就取消，否则货就发出去了。
- 运营/品牌商城的订单状态反映**交易结果**：审核阶段退款还没结果（可能驳回恢复），不应提前跳；只有**退款成功（不可逆）**时交易才真正结束，此时订单关闭成终态才合理。

## 五、各端差异说明 `V1.0`

| 端 | 订单状态联动 | 说明 |
|----|------------|------|
| 供应链管理后台 | **全流程** | 按 R1–R4 联动：发起取消、驳回/撤销恢复、退款成功保持已取消 |
| 供应商管理后台 | **全流程** | 与供应链规则**完全一致**（供应商端为供应链数据权限收窄视图，规则不因端而异） |
| 商城运营后台 | **仅终态** | 审核阶段（R1–R3）订单状态**不变**；退款成功时（R4）订单变为**「已关闭」** |
| 品牌商城 | **仅终态** | 审核阶段（R1–R3）订单状态**不变**；退款成功时（R4）订单变为**「已关闭」** |

> 说明：运营端、品牌商城端在**审核阶段保持不变**（售后尚无结果，不应提前跳变），但**退款成功（不可逆终态）时必须同步关闭**——此时交易真正结束，订单进入「已关闭」终态。这与供应链/供应商"发起即取消"不矛盾：那边是为了拦发货（动作要快），这边是记交易结果（结果落定再记）。

## 六、不适用场景 `V1.0`

> 以下场景**不在本规则范围**，其订单状态联动需另行定义，避免误用"待发货 → 已取消"。

| 场景 | 为什么不适用 | 订单状态如何处理 |
|------|-------------|-----------------|
| **退货退款** | 仅在已签收后发起，发起时订单早已不是"待发货" | 不触发"待发货 → 已取消"。退货退款成功后订单的终态映射另行定义 |
| **换货** | 仅在已签收后发起，发起时订单早已不是"待发货" | 不触发"待发货 → 已取消"。换货出库由系统生成的换货新订单承担，原订单状态另行定义 |
| **已发货 / 已签收后发起的仅退款** | 订单已离开"待发货"，无法"恢复待发货" | 不适用本规则。已发货仅退款涉及物流拦截退回，订单状态联动另行定义 |

## 七、边界与异常处理 `V1.0`

| 编号 | 场景 | 处理规则 |
|------|------|----------|
| **B1** | 订单已发货 / 已签收后才发起仅退款 | R1 **不生效**。此时订单已过"待发货"阶段，不回滚订单状态，按已发货仅退款的物流拦截流程另行处理（见第六章） |
| **B2** | 一个主订单含多个子订单，仅对其中一行发起仅退款 | 按**子订单 / SKU 维度**取消：仅取消被申请的子订单，主订单下其他未申请的子订单**不受影响**，继续正常履约 |
| **B3** | 驳回恢复后再次发起仅退款（反复） | **幂等**：再次发起则再次取消（待发货 → 已取消），再次驳回/撤销则再次恢复。多次往返状态正确，不残留中间态 |
| **B4** | 审核通过后退款失败 | 订单状态**不因退款失败而恢复 / 关闭**。退款失败属于支付链路异常，应通过"重新发起退款"解决；订单保持当前状态（供应链/供应商仍"已取消"），待退款真正成功后才按 R4 关闭 |
